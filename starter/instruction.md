# Sudoku Project Instructions

## Project Overview

This project is a Flask-based Sudoku game that is being refactored from legacy Python code into a modern, maintainable application.

The goal is to preserve existing functionality while adding the required Sudoku, game, persistence, and user-interface features described in the project requirements.

## Code Quality and Style

- Use modern Python practices and clear, readable code.
- Keep functions focused on a single responsibility.
- Use meaningful names for variables, functions, classes, and files.
- Avoid unnecessary code duplication.
- Prefer modular and reusable components.
- Keep Flask routes separate from Sudoku and game logic where practical.
- Use appropriate error handling.
- Handle invalid user input gracefully.
- Add comments when they improve understanding.
- Avoid unnecessary dependencies.
- Preserve existing working functionality unless a change is required.
- Prefer simple and maintainable solutions over unnecessarily complex implementations.

## Project Architecture

Keep the application logically separated into:

- Flask application and routes
- Sudoku generation, solving, and validation logic
- HTML templates
- CSS styling
- JavaScript client-side game interactions
- Automated tests

Do not place all application logic into a single file when it can reasonably be separated into reusable modules.

## Sudoku Requirements

The Sudoku implementation must:

- Generate valid 9x9 Sudoku boards.
- Generate puzzles with exactly one unique solution.
- Support Easy, Medium, and Hard difficulty levels.
- Adjust the number of prefilled cells according to difficulty.
- Keep prefilled cells locked.
- Validate rows, columns, and 3x3 boxes correctly.
- Provide immediate visual feedback for invalid moves.
- Detect when the puzzle has been solved correctly.
- Display a congratulatory completion message.

## Game Features

The final application must support:

- New game functionality.
- Easy, Medium, and Hard difficulty selection.
- A timer that tracks the player's solving time.
- A Hint button.
- A Check button.
- Immediate feedback for invalid entries.
- Completion detection and a congratulatory message.
- A Top 10 scoreboard.
- Player name, completion time, difficulty, and hints used in scoreboard entries.
- Score persistence using browser localStorage.
- A Dark Mode toggle.

## Hint Behavior

The Hint feature must:

- Fill one currently empty cell with its correct value.
- Use the actual solution for the current puzzle.
- Lock the filled cell so that the player cannot modify it.
- Track the number of hints used.

## Check Behavior

The Check feature must:

- Check the player's entered values against the correct solution.
- Highlight incorrect entries.
- Not automatically fill incorrect entries with the correct values.

## Scoreboard

The Top 10 scoreboard must:

- Store completed game results.
- Store player name.
- Store completion time.
- Store difficulty.
- Store number of hints used.
- Sort scores by fastest completion time.
- Keep only the top 10 scores.
- Persist scores using browser localStorage.
- Preserve scores after refreshing or reopening the application.

## Frontend Requirements

The interface should:

- Work on desktop and mobile screen sizes.
- Use responsive CSS.
- Clearly distinguish the nine 3x3 Sudoku boxes.
- Use alternating visual styling for the 3x3 boxes.
- Avoid visible layout shifts.
- Keep text and controls readable.
- Work correctly in both light and dark modes.
- Provide clear visual feedback for invalid entries, hints, and completion.

## JavaScript Guidelines

- Keep client-side logic organized and maintainable.
- Avoid unnecessary global state.
- Validate user input safely.
- Keep UI state synchronized with the current game.
- Handle failed requests or unexpected responses gracefully.
- Use clear event handling for Sudoku cells and controls.

## Testing

Use pytest for Python automated tests.

Testing must be established before major refactoring or feature development.

- Preserve useful existing tests.
- Do not remove tests simply to make them pass.
- Run tests after every major refactor or feature.
- Add tests for important Sudoku generation, solving, and validation behavior.
- Fix the underlying problem when tests fail.
- The test command must be documented in the README.

## GitHub Copilot Usage

GitHub Copilot should be used as an assistant rather than blindly accepting generated code.

For significant changes:

1. Ask Copilot to explain its proposed approach when appropriate.
2. Review the generated code carefully.
3. Check that the suggestion satisfies the project requirements.
4. Accept, modify, or reject the suggestion based on that evaluation.
5. Run the relevant tests after accepting changes.

Do not accept code simply because it was generated by Copilot.

## Development Process

Implement the required features incrementally.

- Make one major change at a time.
- Run tests after each major change.
- Avoid unrelated modifications.
- Preserve working functionality.
- Prefer small, understandable changes.
- If an implementation approach is uncertain, explain the tradeoffs before making the change.
- Prioritize the required project rubric before optional enhancements.

## Optional Features

Do not prioritize optional standout features until all required rubric requirements are complete and tested.

The required project should be fully functional before adding optional features such as Note Mode, solver animation, number tracking, or prompts.json.
